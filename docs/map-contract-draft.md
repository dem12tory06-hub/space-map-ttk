# Формат карты: черновик для обсуждения

СТАТУС: первая серверная модель/API и локальный конструктор реализованы; visitor-viewer участника 2 и компоненты панорам участника 3 ещё не подключены.
До подключения интерфейсов сначала сравнить их фактические файлы и существующие форматы.

## Отдельные сущности

| Сущность | Что описывает |
| --- | --- |
| План | Размеры, комнаты и коридоры; при необходимости исходное изображение плана |
| Место | Стойка, зал, вход и другой объект; название, категория, описание и положение |
| Точка панорамы | Где стояла камера; положение на плане, файл результата, тип проекции и охват |
| Узел прохода | Позиция, через которую посетителю разрешено проходить |
| Ребро прохода | Разрешённое соединение двух узлов; при необходимости промежуточные точки линии |
| Отметка в панораме | Связь с местом и направление на него в панораме |
| Переход между панорамами | Связь двух точек панорамы; не равна ребру прохода |

Положение на плане предлагается задавать координатами `x` и `y` от 0 до 1 относительно
самого плана. Начало — левый верхний угол; x растёт вправо, y вниз. При масштабировании
не учитывать поля вокруг изображения. Направления внутри панорамы хранятся отдельно.

Место связывается с узлом маршрута вручную: соединение должно вести через реальный вход,
а не автоматически через ближайшую стену. Места и панорамы получают независимые постоянные id.
Частичную панораму нельзя выдавать за сферическую 360°.

## Реализованный API первого сценария

- `POST /api/venues` создаёт площадку и возвращает постоянный `id`, один пустой этаж и `ETag` версии `"1"`.
- `GET /api/venues/{id}` загружает площадку по ID. Ответ содержит `ETag` текущей версии.
- `PUT /api/venues/{id}` целиком сохраняет `name` и `floors`. Запрос требует `Authorization: Bearer <ORGANIZER_TOKEN>` и `If-Match: "<revision>"`.
- Места, геометрия плана, точки панорам, узлы маршрута и рёбра маршрута — отдельные массивы. Все объекты и этажи имеют стабильные ID; при добавлении редактор создаёт ID один раз и сохраняет тот же ID при дальнейших правках.
- Координаты и размеры геометрии нормализованы в диапазоне `0..1`; начало координат — левый верхний угол. Геометрия объекта не может выходить за границы плана.
- Удаление объекта: убрать его из соответствующего массива и отправить полный `PUT` с текущим `If-Match`.
- При устаревшем `If-Match` сервер отвечает `412`; повторно загрузите площадку перед сохранением.
- `PUT /api/venues/{venueId}/floors/{floorId}/background` загружает JPG/PNG как бинарное тело запроса; требуется Bearer и текущий `If-Match`. Максимальный размер — 10 МБ, предел декодируемого размера — 50 мегапикселей. API проверяет MIME, сигнатуру/структуру и размеры.
- `GET /api/venues/{venueId}/floors/{floorId}/background/{backgroundId}` отдаёт текущий файл подложки. Это API для редактора; visitor-viewer пока не подключён и подложку посетителю не показывает.
- Visitor URL имеет вид `/map/{venueId}` и содержит только ID. На локальном сервере это локальный адрес; готовой страницы просмотра посетителя пока нет.

Необязательная подложка находится в `floor.plan.background`:

```json
{
  "id": "<backgroundId>",
  "mediaType": "image/png",
  "width": 2400,
  "height": 1600,
  "visible": true,
  "opacity": 0.65
}
```

Сам файл не кодируется в JSON. Он хранится в `DATA_DIR/backgrounds/<venueId>/<backgroundId>.png` (для JPEG расширение `.jpg`). Старый план без поля `background` валиден. Если полный `PUT` от прежнего клиента не содержит `plan.background`, сервер сохраняет текущую подложку; видимость и прозрачность сохраняются вместе с площадкой. При замене сначала атомарно записывается новый уникальный файл и метаданные; при отказе предыдущая подложка остаётся доступной. Новая подложка скрыта только на visitor-viewer по умолчанию, поскольку этот viewer ещё не реализован.

Файл `venues.json` хранится вне каталога приложения. По умолчанию используется `~/.local/share/space-map-ttk/venues.json`; `DATA_DIR` задаёт другой каталог. Подложки лежат рядом в `backgrounds/`. Запись выполняется во временный файл с последующей атомарной заменой. Не размещайте данные внутри каталога, который заменяется при деплое.

Операции записи требуют секрет `ORGANIZER_TOKEN`. Если он не задан, сервер отвечает `503` и не принимает записи. Не включайте токен в клиентский JavaScript. Bearer-токен нельзя отправлять через публичный HTTP: для удалённой работы сначала настройте HTTPS.

### Пример вызовов

Создать площадку:

```http
POST /api/venues HTTP/1.1
Content-Type: application/json
Authorization: Bearer <ORGANIZER_TOKEN>

{"name":"Демо-площадка"}
```

Ответ `201` включает `id` площадки и пустой этаж. Затем загрузить её:

```http
GET /api/venues/<venueId> HTTP/1.1
```

Передать полученный `ETag` в `If-Match` при сохранении:

```http
PUT /api/venues/<venueId> HTTP/1.1
Content-Type: application/json
Authorization: Bearer <ORGANIZER_TOKEN>
If-Match: "1"

{
  "name": "Демо-площадка",
  "floors": [{
    "id": "<floorId>",
    "name": "Этаж 1",
    "plan": {
      "id": "<planId>",
      "width": 1,
      "height": 1,
      "elements": [{
        "id": "<elementId>",
        "type": "table",
        "name": "Стол A",
        "x": 0.1,
        "y": 0.2,
        "width": 0.2,
        "height": 0.1,
        "rotation": 0
      }]
    },
    "places": [{
      "id": "<placeId>",
      "type": "registration",
      "name": "Регистрация",
      "category": "Сервис",
      "description": "У главного входа",
      "x": 0.5,
      "y": 0.9
    }],
    "panoramaPoints": [],
    "routeNodes": [],
    "routeEdges": []
  }]
}
```

Допустимые типы элементов плана: `zone`, `table`, `stand`, `stage`, `partition`. Типы мест: `entrance`, `registration`, `service`. Ветки панорам и маршрутов пока сохраняют отдельные сущности, но их пользовательские сценарии ещё не реализованы.

API проверяет структуру и координаты и отклоняет неизвестные поля. Сообщение «Сохранено» показывать только после успешного ответа `PUT`. Секрет доступа должен выдаваться организатору через безопасный механизм; не хранить его в публичном коде.

## Подготовка переноса одной площадки на Aeza

Перенос не выполнялся. Перед переносом выяснить фактический `DATA_DIR` службы. На локальном экземпляре экспортировать только нужную площадку ответом `GET /api/venues/{venueId}`; файл подложки копировать отдельно из `DATA_DIR/backgrounds/{venueId}/` по ID и типу из `plan.background`. Текущий browser-test запуск использует временный `%TEMP%\space-map-constructor-...`; эта копия предназначена только для проверки, а не для постоянной работы.

На Aeza сначала остановить `space-map` и сделать резервную копию всего каталога данных, включая `venues.json` и `backgrounds/`. Затем добавить экспортированный объект в существующий `venues.json` (конверт `{"schemaVersion":1,"venues":[...]}`), не заменяя весь файл; если такой ID уже есть, остановиться и сравнить данные, не перезаписывать запись автоматически. Скопировать файл подложки по тому же относительному пути. После проверки JSON и прав доступа запустить службу и проверить `GET /api/venues/{venueId}`, revision и загрузку файла. После успешной проверки сохранить копию до отдельной оценки отката. Пароли и токены в этих командах не выводить.

1. Форматы и технологии, которые уже используют участники 2 и 3.
2. Точное содержимое полей и связи между сущностями, включая редактируемую геометрию плана.
3. Способ подключения экранов и размещения их стилей.
4. Общие цвета, шрифт, отступы и размеры элементов на телефоне.
